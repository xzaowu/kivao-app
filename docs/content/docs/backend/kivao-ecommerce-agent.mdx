# KIVAO 电商 Agent

电商 Agent 是完整入口，产品套图只是其中一种创作用途。前台 `/ecommerce-agent` 包含白底图、单图、主副图、产品套图、详情图与营销物料，以及商品素材、平台与语言、视觉方向、逐张策划、生成作品、连续轮次和导出。商品视频按钮把已完成作品作为首帧交给现有视频工作台；跳转本身不生成视频、不扣费。

旧版商品套图的前台、后台导航和开放开关已移除。`/ecommerce` 跳转 `/ecommerce-agent`，`/admin/ecommerce` 跳转新配置页，旧项目参数不会误传为新项目 ID。已有项目和轮次保留在原表，不删除或强制转换，也不混入新模块的项目列表。旧业务 API 和迁移保留，用于历史数据保全；后续如需历史导入再单独评估。

## 来源与适配

源码来自上游 [v1.8.5](https://github.com/ddcat-ai/open-ai-canvas/releases/tag/v1.8.5)，冻结提交 `ac5e01cab55184fa9f202fe6349a5884411b4114`。KIVAO 基线是 `917967f3e333a557a9c19105f1c3180d9cf9476d`，开发分支为 `dev/kivao-ecommerce-agent`。按模块移植，不合并上游 main，不引入上游完整 Schema 100，不修改 Agent Runtime。

新增代码的 Go 标识及表前缀使用 `CommerceStudio` / `commerce_studio_`，前端页面目录为 `commerce-studio`，避免与 KIVAO 旧版 `Ecommerce` 冲突。原有内部协议标识、嵌入资料来源和许可证保留。新增依赖仅为图像解码所需的 `golang.org/x/image v0.40.0`。

## 管理员设置

- 功能开放中独立设置“电商 Agent”和“商品视频”，缺失字段默认关闭。商品视频还要求原有视频工作台开放。
- `/admin/ecommerce-agent` 设置商品识别与视觉方向、整套策划所使用的平台文本模型及思考意图；应使用支持参考图片、已定价且当前用户可访问的模型。
- `/admin/ecommerce-agent/library` 管理内置知识、分类与技能；相邻 `/library/skills` 和 `/library/categories` 保留详细管理入口。启动只装载随代码提供的资料。仅在管理员明确从 GitHub 安装技能后，按该来源定期检查更新；随代码提供的资料和本地上传文件不会自动联网，也不执行导入的代码。
- 用户私有技能仍只对本人可用。用户申请公开的技能仍须经过 KIVAO 管理员审核后才可安装，不能绕过既有上架审核。

## 任务、数据与资源

识别和策划使用现有文本任务、事件流、报价和计费；逐图生成使用原生图片工作台任务。没有开放上游独立的 `/agent/generate/stream` 等另一套执行接口，也不启用一次计费内的并行多模型请求。历史读取、页面刷新、导出与视频跳转不创建新生成任务。

图片初次提交使用当前项目、轮次和图片标识形成固定批次；服务端同时核对完整请求指纹，丢失回执后重试不会再次预留费用。修改后的单图重生成沿用独立请求回执和未确认阻断，不能将不确定的请求当成失败自动重发。已被供应商接受的任务及不确定费用继续走现有核对路径。

需要新增 KIVAO Schema 81 的九张 `commerce_studio_*` 表，保留迁移 78、79、80 的名称与校验和。新项目和轮次计入既有结构化数据额度；保存参考素材与素材删除采用相同的行锁及归属校验。项目、历史、分析和结果中的资源引用纳入删除保护。

长图裁片和作品导出新增 `purpose=ecommerce-export`：只允许读取当前用户已就绪的 PNG/JPEG/WebP 图片原件，单图不超过 32 MiB，服务端代理返回，不把对象存储凭据交给浏览器。不改变其他资源用途的交付方式。

前端平台规则直接引用后端同一份 `platform_knowledge.json`。根 Dockerfile 明确复制该文件；源码开发容器也须包含它，不能只挂载 `web/` 后宣称构建环境等价。

## 验证与后续发布

### 本地试用顺序

1. 在后台“电商 Agent 配置”查看开放状态和阶段模型。日常本地环境继续使用虚拟文本、图片模型；它们用于检查操作、任务与保存流程，输出是固定示例。
2. 从前台“电商 Agent”新建项目，先用“产品套图”上传一张商品图，填写明确的外观与已知卖点，选择两张图片。完成视觉方向选择、策划、出图、单图查看与 ZIP 导出，再刷新页面检查作品仍在。
3. 分别切换白底图、单图、主副图、详情图和营销物料。检查数量、对应素材要求和专属选项是否符合用途；营销物料还应检查物料配置弹窗。切换类型、打开配置和查看历史不应创建生成任务。
4. 在手机上切换“创作／作品”，检查上传、滚动、底部操作及明暗主题；打开历史再关闭，确认页面仍可操作。商品视频仅验证携带图片进入现有视频工作台，不在此次试用中提交真实视频。

本地虚拟模型支持风格借鉴与长图逐屏参考的模拟返回，便于检查资料上传、方案接收和来源对应。长图固定每张来源返回三屏，摘要明确标识为模拟；它不会读取图片内容，不能用来判断真实分屏、模特相似度或版式还原质量。

真实模型小样本验收已安排到部署验收阶段，不作为继续本地开发的前置条件。届时在明确授权的模型、数量和费用范围内，优先检查产品套图与详情图的商品一致性、文字、策划 JSON 和实际费用；模特参考、长图借鉴、营销物料分别记录结果。虚拟模型通过不能替代这些质量结论。旧项目保留在原数据表中，不能用旧项目 ID 打开新项目。

本轮仅本地开发及虚拟模型验证。真实模型的 JSON 稳定性、长图识别、商品外观一致性、文字准确性与真实费用尚需授权后单独验收；虚拟图片不证明模型质量。商品视频只复用现有视频工作台，不提供新的视频协议。

本地浏览器已验证商品上传、四个视觉方向、两张逐图生成、ZIP 导出、刷新和历史不重复提交、关闭功能后历史读取、商品视频跳转、后台配置及旧地址重定向。桌面与手机通过实际主题开关检查明暗模式；历史弹窗同时验证普通动画和减少动态效果下关闭后不会遮挡页面。SQLite 与隔离 PG17 的 80→81 升级验证不改写原表数据及既有迁移记录。

未来发布需要配套前后端、Schema 81 升级和备份验证。当前生产镜像不能据此直接作为 Schema 81 的应用回退镜像；需另行准备能读取 81 且可关闭新模块的回退版本，或明确授权恢复一致性备份。禁止下调迁移账本、删除新表或覆盖新写入来冒充回滚。本轮不推送、发布镜像或改动生产。

### 发布准备检查

- 电商模块本地提交为 `245c7fc39febee8b2c4f76c677d9fec82a222621`。现有发布配置仍使用 1.0.5 的旧候选、发布分支和 Schema 79，不能用它为本模块生成发布锁；待本轮范围冻结后，再绑定最终候选 SHA、Schema 81 和对应 CI。
- 发布来源检查目前在“工作区必须为干净候选”处拒绝执行：原有发布配置尚有独立修改，未覆盖或纳入电商提交。该结果不代表后续镜像、权限及发布检查已通过。
- 前端 Dockerfile 已包含共用平台规则 JSON；后端通过 `go:embed` 包含平台规则及离线知识资料。此处为构建输入核对，不能替代未来三个正式候选镜像的构建、身份与运行验收。
- 部署验收还须检查新功能开关、两个实际文本阶段模型、图片模型、真实输出及账务。功能开关缺省关闭，旧模型配置不会自动转成新模块阶段配置。
