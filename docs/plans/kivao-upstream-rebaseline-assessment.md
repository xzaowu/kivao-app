# KIVAO 上游基线重整评估

## 结论与范围

建议停止默认按十条提交逐项移植，改为固定上游稳定版本、叠加 KIVAO 必要定制。先做本地试迁，再决定完整迁移和发布。当前评估足以支持这一路线；尚未证明新基线可以接管现有数据库，也没有新的镜像、生产或付费调用验收结论。

后续取舍已收敛为[定制瘦身清单](kivao-customization-pruning.md)。所有者明确选择优先采用上游手机/桌面布局，并采用多页面助手入口；原有仅画布助手和旧版布局不再作为迁移保留要求。固定 `3979305c` 是当前计划的本地试迁候选，包含后续多用户与资源保护，尚未切换源码或完成候选运行验证。

本轮只读取代码、发布信息和本地历史记录，并编写计划。当前开发分支及四份原有未提交修改保留；没有切换工作区、修改业务实现或数据库。生产状态没有重新读取，生产实际 Schema、活跃运行和数据量必须在未来获授权的部署预检中核实。

## 必须保留的定制，以及收敛方式

| 定制组 | 必须保留的行为 | 在新基线的处理方式 |
| --- | --- | --- |
| KIVAO 品牌 | 初始标题、图标、Logo/SEO、自定义外观回退、服务协议名称、导出标识及存储前缀默认值 | 优先使用外观设置和集中默认值，不全局替换内部 `yingce` 标识或许可证 |
| 登录与游客 | 登录注册弹窗、游客入口、登录后草稿和账号隔离 | 复用上游认证主体；只补缺失交互与隔离，不复制旧 auth 包覆盖新版 |
| 创作界面 | 手机可用性、输入与场景能力、模型选择和节点开关 | 优先采用上游布局及多页面助手，不再复刻旧排版或仅画布限制；只补必要业务差异 |
| 运营内容 | 后台工具入口、效果素材组/必填/数量、注意事项、多个示例、灵感增删改查和展示 | 先比较 JSON/API 合同，再映射旧配置；必须保留配置数据及素材引用 |
| 管理权限 | 全站插件控制、用户端入口取舍、技能公开审核及上下架 | 保留后端权限与公开准入；后台 UI 可沿用新版布局 |
| 自有供应商协议 | 坤肉视频、坤肉音频、独立深度动作捕捉及对应节点/工具 | 尽量作为独立插件和小范围注册；保持既有协议 ID 和模型路由，比较包格式后再复用 |

## 数据兼容是一次性主工程

### 已确认的迁移编号冲突

| 编号 | KIVAO | 上游 v1.8.5 |
| --- | --- | --- |
| 78 | `skill_publication_review` | `drama_cast_voice_looks` |
| 79 | `payment_order_method` | `ecommerce_agent_and_knowledge` |
| 80 | `kivao_ecommerce_project_rounds` | `payment_order_charge_method` |
| 81 | `kivao_commerce_studio` | `ark_portrait_assets` |

证据为两边固定提交的 `backend/internal/database/migrations.go`。不能把 81 改为 100、覆盖校验和或删除迁移记录后启动新程序；上游服务默认可自动迁移，第一次试迁必须使用独立空目录/库并明确控制迁移，不能误挂现有日常开发库。

推荐的长期目标是：保留上游原生迁移编号；真正需要的新 KIVAO 数据扩展使用独立命名和独立迁移记录。过渡应完成一次可审计的数据转换，避免每个上游版本都重编号整套迁移。

转换的两个候选路径：

- **隔离目标库转换**：新建官方目标结构，把恢复副本的业务记录按字段映射导入，保留用户、资源、模型、订单等 ID 和时间戳，并记录全部转换对应关系。先作为结构参考和转换验证路径；未来是否切换生产连接另行决定。
- **原地转换**：只在副本完成结构差异、历史账本保全和转换重跑验证后评估。若必须改动官方历史记录才能放行，要使用专门的转换程序保留原账本和证明每个已完成结构步骤，不能伪造已运行上游迁移。当前未选择或实现此路径。

前者更易隔离验证，后者可能减少部署路径变化。现阶段不承诺原地转换，也不为追随上游而清空或重装生产业务数据库。

### 必须逐项映射的数据

| 数据 | 转换时必须证明 |
| --- | --- |
| 用户、渠道、模型、定价和分组 | ID、启用状态、模型路由、免费档、计费单位及实际售价不被默认值覆盖 |
| 积分、订单、支付通知及对账记录 | 余额/冻结额/流水一致、订单仍引用原配置版本；新增支付实收字段须按历史语义转换 |
| `.settings-key` 与加密字段 | 原文件保留，密文及加密用途/AAD 兼容性实测；只报告解密成功与否，不输出明文 |
| 工具、效果、灵感、示例、公告与资源引用 | JSON 不被新版截断，资源 ID、文件和使用关系一致；关闭功能不等于删除配置 |
| 技能与公开状态 | 待审核/驳回/下架不能变成公开可安装；既有管理员修改和包文件保留 |
| 电商项目 | 原 `ecommerce_*` 两张最小版表与 `commerce_studio_*` 新模块分开映射；不能因为官方同名表就直接覆盖。JSON 的资源、任务与轮次引用也须转换 |
| 画布、项目、撤销历史和媒体 | 新节点模型、旧前像/撤销哈希、深度捕捉节点、导入导出及持久资源一致；不能仅重新计算哈希绕过检查 |
| Agent 运行 | 当前 KIVAO 工具合同 v8，上游发布说明为 v11；已结束历史保留，活动或待审批旧运行必须先收尾，不在新合同下继续执行 |

文件与数据库必须来自同一可解释的一致性恢复点。当前尚未使用生产副本执行本次转换，也未重新统计生产数据量，不能给出转换耗时或停机承诺。

## 建议执行顺序

1. **最小试迁**：在定制瘦身清单固定的上游候选 `3979305c` 上准备独立开发分支，使用同一日常源码目录，不长期增加多份工作树。先保留当前未提交资料，再切换；使用全新本地数据目录。完成官方原生 Web/Backend/Agent 构建、虚拟服务运行、KIVAO 默认品牌和一个自有协议插件的加载验证。先检验新底座及扩展点，不立即搬全套定制。
2. **收敛定制**：按上表逐组补回必要差异，优先后台配置，再到页面行为。新基础功能采用上游实现；保持模板/数据键、协议 ID 和权限要求。把旧回归场景用于新版实际调用路径，不能靠修改断言掩盖行为退化。
3. **转换演练**：先用合成旧结构数据验证字段和关联，再在另获授权的真实备份副本上恢复、转换、校验、重跑和回退。副本使用独立 PG17、目录及网络；启动后台组件前验证出站受控，禁止真实模型、支付、通知、MCP 或其他外部写入。
4. **发布与部署验收**：冻结新候选 SHA，沿用现有自有发布机制调整版本/CI/镜像锁。真实模型小样本质量和费用核对按用户决定放到部署验收，调用模型与预算另行明确；之后才评估生产预拉、维护窗口、最终备份、切换与回退。

当前评估仅完成步骤前的取舍与风险定位。没有开始这些步骤，也没有新的开发分支、镜像或运行验收。

## 后续日常同步

- 官方新发布是同步输入，单轮固定 tag/SHA；main 只用于观察问题修复，紧急补丁明确记录来源与退出条件。
- 开发同步与生产升级分开。先验证一轮稳定基线，避免在同一试迁中不断追新。

- 已发布分支和标签不改写；main 不用来直接覆盖生产。当前开发分支保留为旧路线对照，未来新基线单独建立开发分支。

## 放行判断

- **新基线路线：建议采用。** 当前证据支持开始小范围本地试迁，而不是继续逐个移植大模块。
- **生产迁移：尚不具备条件。** 数据转换、活动运行收尾、真实副本恢复和成对回退未完成。
- 不依据路径数承诺具体天数。先用最小试迁验证扩展点和自有协议兼容，再据实际补丁和数据差异估算完整工作量。
